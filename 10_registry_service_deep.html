Роль в архитектуре ПТК

Registry — «телефонная книга» Системы. Хранит: кто участвует (participants), что предлагает (tariffs), с кем работает (bindings), и готов ли (gate). Все остальные сервисы обращаются к Registry за данными участников.

Тарифы: оферта в реестре (ст. 3.2)

Каждый участник (кроме Организатора) публикует тарифы самостоятельно. Тариф = публичная оферта внутри Системы: «готов оказать услугу X за Y рублей».

ПРАВИЛА ТАРИФОВ 1. Кто назначает: сам участник (не Организатор) 2. Формат: service_type + unit + rate (ст. 3.2) 3. Публичность: видны всем селлерам при выборе оператора 4. Изменение: уведомление за notify_days (мин. 14 дней) 5. Незадним числом: заказы, принятые до изменения → по старому тарифу 6. История: все версии хранятся (valid_from → valid_to) ТИПЫ ТАРИФОВ: ┌──────────────────────────┬──────────────────┬───────────┐ │ service_type │ unit │ пример │ ├──────────────────────────┼──────────────────┼───────────┤ │ ASSEMBLY │ PER_ITEM │ 200₽/ед │ │ ASSEMBLY_BULK │ PER_ITEM │ 150₽/ед │ │ STORAGE │ PER_PALLET_DAY │ 50₽ │ │ RETURN_HANDLING │ PER_ITEM │ 300₽ │ │ DELIVERY_ZONE_1 │ PER_ORDER │ 350₽ │ │ DELIVERY_ZONE_2 │ PER_ORDER │ 500₽ │ │ DELIVERY_ZONE_3 │ PER_ORDER │ 800₽ │ │ TRUNK_MSK_SPB │ PER_PALLET │ 1500₽ │ │ TRUNK_MSK_KRD │ PER_PALLET │ 2200₽ │ │ ACCEPTANCE │ PER_PALLET │ 100₽ │ │ ORGANIZER_FEE │ PERCENT │ 0.2% │ └──────────────────────────┴──────────────────┴───────────┘ API тарифов: GET /api/v1/tariffs?participant_id=X — тарифы участника GET /api/v1/tariffs?role=FULFILLMENT — все тарифы роли (для выбора) POST /api/v1/tariffs — создать/обновить тариф GET /api/v1/tariffs/{id}/history — история изменений

Привязки: селлер ↔ операторы (ст. 3.3)

ПРИВЯЗКА (BINDING) При настройке магазина (wizard, задача 1.1): 1. Селлер видит список операторов по каждой роли 2. Для каждой роли показаны: название, тарифы, SLA, рейтинг 3. Селлер выбирает (или система назначает из гейта) 4. Binding записывается в реестр Структура: { seller_id: "PTR-12345", fulfillment_id: "PTR-67891", // 3PL-Сервис logistics_id: "PTR-88901", // Курьер-Экспресс trunk_id: null, // нет (один регион) warehouse_id: null, // null = фулфилмент совмещает active: true, bound_at: "2027-07-01" } Смена оператора (ст. 3.3.2): 1. Селлер в ЛК нажимает «Сменить фулфилмент» 2. Видит список: другой оператор, тариф 180₽/ед, SLA 12ч 3. Выбирает → текущий binding.active = false 4. Новый binding.active = true 5. Заказы в обработке → по старому 6. Новые → по новому 7. Нового договора НЕ нужно Ограничения: • 1 активный binding на роль на селлера • Нельзя привязать SUSPENDED/EXITED участника • Волна 0–1: автоназначение (ближайший из гейта) • Волна 2+: свободный выбор из ≥2 операторов

Приёмка в реестр (ст. 4, 13.1)

ПРИЁМКА УЧАСТНИКА Для селлера (ст. 13.1.1): 1. Форма /join: ИНН + телефон 2. ФНС API → KYC Level 1 3. Click-wrap акцепт (ст. 2.7) 4. Registry.CreateParticipant: { role: SELLER, status: ACTIVE, seller_group: 1|2|3 } 5. → Wizard → Магазин → Товары → Go Live Для оператора (фулфилмент, логистика): 1. Заявка через Admin Panel (или API) 2. KYC Level 2 (проверка ИНН + учредители + лицензии) 3. Договор присоединения (КЭП для ООО) 4. Публикация тарифов в реестре 5. SLA-соглашение (приложение) 6. Registry.CreateParticipant: { role: FULFILLMENT, status: ACTIVE } 7. Тестовый прогон (webhook, API интеграция) 8. → Готов к привязке Для банка: 1. Переговоры (Организатор ↔ Банк) 2. Договор на эскроу API 3. Тестовая интеграция (sandbox) 4. Registry.CreateParticipant: { role: BANK, status: ACTIVE } 5. → BankAdapter подключён в Clearing Engine

Гейт готовности (ст. 13.2)

Перед запуском привлечения селлеров (Волна 1) — проверка: все инфраструктурные роли закрыты.

ГЕЙТ: УСЛОВИЯ ПРОХОЖДЕНИЯ Registry.CheckGate() → GateResult Условия: ┌─────────────────────────────────────────────────────────────┐ │ Роль │ Мин. участников │ Статус │ Проверка │ ├──────────────────┼─────────────────┼────────────┼───────────┤ │ FULFILLMENT │ ≥ 1 (идеал: 2) │ ACTIVE │ ✓/✗ │ │ LOGISTICS │ ≥ 1 │ ACTIVE │ ✓/✗ │ │ ORGANIZER │ = 1 │ ACTIVE │ ✓/✗ │ │ BANK (Трек B) │ ≥ 1 │ ACTIVE │ ✓/✗ │ └──────────────────┴─────────────────┴────────────┴───────────┘ + У каждого ACTIVE участника: • Опубликованы тарифы (≥ 1 tariff) • SLA подписан • Webhook / API протестирован Результат: GATE_PASSED: все роли закрыты → можно привлекать GATE_PARTIAL: Трек A (без банка) → можно, но без эскроу GATE_BLOCKED: нет фулфилмента/логистики → нельзя Корректив К2 (ст. 13.2): Два фулфилмент-оператора с первого дня — для переговорной позиции. Gate PASSED при ≥1, но RECOMMENDED при ≥2.
