# marketplace-api

API и фронтенд Системы. Пилот — `massamadre.ru`.
Спринт 0: замена Google Sheets на PostgreSQL + REST API. Пилот работает
непрерывно, данные переезжают из таблиц в базу двойной записью.

| Страницы | `https://kuzin4u.github.io/marketplace-api/` (GitHub Pages) |
| База | Supabase, EU Frankfurt |

> База находится за пределами РФ. Задача 0.0 плана реализации — перенос
> в российскую юрисдикцию; срок привязан к задачам 0.7–0.8, переносу

> необратима, поэтому порядок: сначала площадка, потом схема на ней,
> потом история.

## Схема: порядок применения

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f schema/01_schema.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f seed/02_seed_massamadre.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f schema/03_integrity.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f schema/04_suborders_consents.sql
```

Вся цепочка проверена на PostgreSQL 16.

**03_integrity** добавляет ограничения и триггеры, структуру не меняет.
Резерв не больше остатка, ИНН уникален в паре с ролью, позиция товара
в заказе не дублируется, итог заказа сходится, отзыв только от участника
сделки, аудит-лог действительно неизменяем. Обратима: ограничения снимаются.

**04_suborders_consents** — задача 0.1. Заказ распадается на родительский
и подзаказы по числу продавцов; появляется неизменяемая таблица согласий;
деньги переходят в целые копейки; уровень участия сделки защищён храповиком.
**Необратима** — колонки удалены, суммы пересчитаны. Перед применением
на боевой базе прогоняется `ops/dump-restore-verify.sh`.

## Маршруты

Базовый префикс — `/api/v1`.

### Покупатель

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/shop/{slug}` | магазин по адресу |
| GET | `/shop/{slug}/products` | товары магазина (`?cat`, `?sort`, `?page`) |
| GET | `/sku/{id}` | карточка товара — источник правды |
| GET | `/catalog/search` | каталог Системы (`?q`, `?cat`, `?price_min`, `?sort`) |
| GET | `/catalog/shops` | каталог магазинов |
| GET | `/catalog/categories` | дерево категорий |
| POST | `/cart/add` | добавить в корзину, атомарное резервирование |
| POST | `/orders` | создать заказ, автоматический клиринг |
| GET | `/orders/{id}` | заказ с позициями и расщеплением |

### Продавец

Требуют заголовка `Authorization: Bearer <token>`; токен выдаёт
`POST /auth/login`. `seller_id` берётся из токена, а не из URL или тела.

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/auth/login` | вход, выдача JWT |
| POST | `/participants` | создание участника |
| POST | `/shops` | создание магазина |
| GET | `/seller/products` | товары продавца |
| POST | `/seller/products` | создать товар |
| PATCH | `/seller/products/{sku_id}` | обновить товар |
| GET | `/seller/stats` | статистика |
| GET | `/config/{slug}` | конфиг магазина для рендеринга витрины |
| GET | `/smoke-test` | штатный смоук-тест |

Проверка контура целиком: `bash ops/smoke.sh <адрес>`.

> Маршруты `channels-api.js` и `customers-api.js` в перечень не входят:
> первый не врезан в `server.js`, второй нигде не описан.

## Что миграция 04 ломает в коде

Исчезли три колонки: `skus.price`, `orders.seller_id` и `orders.shop_id`,
`order_items.order_id`. Код, который их просит, вернёт ошибку.

Временная опора — представление `orders_flat`: отдаёт заказ в прежней
плоской форме, запросы вида «заказы продавца» продолжают работать.
Убирается в задаче 0.3, когда слой доступа перепишется на подзаказы.

Новое требование: **заказ и его позиции пишутся в одной транзакции**.
Проверки сходимости отложены до фиксации, и вставка заказа отдельным
запросом упадёт.

Загрузчик истории обязан объявить себя переносом, иначе признак
«до введения согласий» не поставить:

```sql
SET LOCAL app.history_migration = 'on';
```

## Конфигурация фронта

Адрес API живёт в `config.js`, константа `PROD_API`. Страницы читают
`window.API_BASE`.

* переезд API — правка одной строки, а не десяти файлов;
* страница, открытая с `localhost` или из файла, сама целится
  в `http://localhost:3000`;
* проверка против другого контура без правки кода:
  `shop-form.html?api=https://stage.example.com`, сбрасывается через
  `sessionStorage.removeItem('API_OVERRIDE')`.

Подключение — в `<head>`, до основного скрипта:

```html
<script src="config.js"></script>
```

При добавлении новой страницы: подключить `config.js` и брать
`window.API_BASE`. Строку с адресом в код не писать.

## Известные расхождения

Полный перечень с привязкой к документам пула — `ops/code-map.tsv`.

1. **`JWT_SECRET` не выставлен** в боевом окружении: подпись работает
   на значении по умолчанию. От площадки не зависит, закрывается сейчас.
2. **Код оперирует `price` в рублях**, база после миграции 04 хранит
   `price_kop` в копейках. Правится в задаче 0.3.
3. **Экономическая модель в сиде устарела:** вознаграждение Организатора
   0.2%, фонда поддержки сети нет. Зафиксировано совокупное удержание
   12.5% = 0.5% Организатору + 12.0% в фонд.
4. **Формула клиринга в двух местах:** `calculateClearing` в `api/server.js`
   и её ручное воспроизведение в `pipeline-model-interactive.html`.
5. **`channels-api.js` не врезан** в `server.js`.
6. **`customers-api.js` не описан** ни в одном документе пула.
7. **`seller-routes.js` лежит в корне**, а не в `api/`.
8. **Схема построена под Правила ред. 2**; действующая — третья.

## Реестр соответствия

`ops/code-map.tsv` отвечает на вопрос «какой документ описывает какой код
и сверялись ли они». Лежит в репозитории, а не в пуле, потому что меняется
вместе с кодом.

Правило: меняешь логику — в том же коммите ставишь дату в колонке
«сверено» либо помечаешь документ как расходящийся. Реестр не обязан
быть зелёным; он обязан быть честным.

```bash
python3 ops/render-code-map.py     # собрать HTML-вид для пула
```

Описательная часть — правила, архитектура, модели, планы — живёт в пуле
документов и сюда не копируется.
