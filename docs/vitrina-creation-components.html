Как рождается витрина магазина

Что с чем взаимодействует, когда селлер создаёт магазин и наполняет его товарами — от формы в личном кабинете до готовой витрины, которую видит покупатель и агент. Все связи по фактическому контракту server.js.

формы ЛК (клиент) Marketplace API (server.js) база (Supabase) витрина и агент (потребители)

Как читать схему

Четыре зоны слева направо: формы личного кабинета (селлер вводит) → Marketplace API (server.js принимает и проверяет) → база Supabase (данные ложатся) → витрина и агент (читают и показывают). Сплошные стрелки — запросы, пунктир — связи между таблицами по ключам.

Порядок и зависимости составных

ШагКтоМаршрутЧто создаётЗависит от

2SKU-CRUDPOST /seller/:id/productsтовары в skusу продавца должен быть магазин

GET /shop/:slug/products		— (только читает)магазин + товары ACTIVE

Ключевая зависимость — цепочка ключей. Товар нельзя создать раньше магазина (проверка «у продавца есть магазин»), магазин нельзя создать без участника (проверка «seller_id существует»). Поэтому порядок жёсткий: participant → shop → sku. Витрина и агент в конце только читают — они ничего не создают, а собирают готовое из базы через API.

Две «видимости» товара. visible_shop — показывать ли товар на витрине магазина; visible_catalog — отдавать ли его агенту в каталог Системы. Форма SKU-CRUD ставит обе в зависимости от статуса ACTIVE, поэтому DRAFT-товар не появляется ни там, ни там — это и есть проверка сквозного сценария из уровня 4.
