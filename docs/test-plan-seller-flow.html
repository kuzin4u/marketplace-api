Главное ограничение. Из среды сборки (контейнер) живой API недоступен — egress-прокси блокирует onrender.com (host_not_allowed). Поэтому уровни 3–4 (реальные вызовы API, база, витрина) выполняются на вашей стороне, в браузере и Supabase. Контейнер закрывает только уровень 1 (логика).

Базовый прогон — 22 PASS / 0 FAIL. Расширенный набор злых граничных случаев (test-forms-extended.js, node test-forms-extended.js) — 16 PASS / 0 FAIL. Итого 38 автопроверок.

Уровень 2 — браузер (ручной чек-лист)

jsdom не рисует пиксели и не знает про мобильный экран. Откройте обе формы в Chrome (и на телефоне), пройдите чек-лист. Инструмент: браузер + F12 DevTools (вкладки Console и Network).

Shop Form

  • Все 4 экрана открываются, прогресс-бар подсвечивает текущий шаг
  • Превью-карточка меняет цвет/название/адрес в реальном времени при вводе
  • Загрузка логотипа: картинка появляется и в дропзоне, и в превью
  • Свотчи цвета переключают акцент обложки превью
  • Проверка slug: индикатор «проверяем… → свободен/занят» отрабатывает без зависаний
  • Кнопка «Далее» заблокирована, пока slug не проверен
  • На узком экране (телефон) превью уходит вниз, форма не ломается
  • Console без красных ошибок на всём пути

SKU-CRUD

  • Переключение вкладок «Быстрое добавление» / «CSV» работает
  • Фото товара загружается и показывается в карточке
  • AI-подсказка заполняет поля, toast появляется и гаснет
  • Карточка товара: статус, цена, подсветка низкого/нулевого остатка
  • Модалка редактирования открывается, сохраняет, закрывается по фону и «Отмена»
  • Удаление убирает карточку и уменьшает счётчик
  • Фильтр по статусу показывает нужное подмножество
  • CSV с «грязными» строками (пустые, без цены) — импортирует только валидные

Уровень 3 — живой API и база

✓ ПРОЙДЕН ВЖИВУЮ (20.08.2026). На живом Render + Supabase создана и прочитана обратно вся цепочка: продавец PTR-948a2938 → магазин SHOP-test-qa-1 → товар SKU-e7013d8b → виден в витрине (total:1). Вскрыто 3 расхождения формы vs база: seller_group числовой; category_id — реальный id из справочника; sku-crud нужен список 7 категорий из /catalog/categories. Все три учтены в формах и Боевая авторизация (JWT) · справочнике.
Маршруты уже есть на сервере — отдельный модуль не нужен. Сверка с реальным server.js: POST /shops, POST /seller/:seller_id/products, POST /orders, GET /shop/:slug уже реализованы. Настоящее расхождение было в формах — они слали неверные имена полей (title вместо brand_name, price_kop вместо price, без seller_id). Формы приведены к реальному контракту — перечень в справочнике маршрутов. Осталось: создать тестового продавца (POST /participants), подставить его seller_id и прогнать создание магазина и товара на живом Render + Supabase.

Здесь проверяется то, что в формах пока «best-effort»: реально ли создаётся запись. Инструменты: curl/Postman и SQL-панель Supabase.

3.1 Существуют ли маршруты

Формы обращаются к трём маршрутам. Сначала убедитесь, что они есть в server.js на Render:

curl -i https://marketplace-api-ujfh.onrender.com/api/v1/shop/massamadre
curl -i -X POST https://marketplace-api-ujfh.onrender.com/api/v1/shops \
  -H 'Content-Type: application/json' \
  -d '{"title":"Тест","slug":"test-qa-1","accent_color":"#8B4513","regions":["Москва и МО"],"fulfillment":"3PL-Сервис"}'
curl -i -X POST https://marketplace-api-ujfh.onrender.com/api/v1/seller/products \
  -H 'Content-Type: application/json' \
  -d '{"title":"Тест-товар","price_kop":45000,"stock":10,"category":"Хлеб"}'
Если маршрут отвечает 404. Значит его нет в server.js — это известный пробел: в памяти проекта отмечено, что POST /api/v1/orders ещё не поднят, и /shops, /seller/products нужно сверить так же. Форма при этом не падает (best-effort), но запись не создаётся — это то, что уровень 3 и должен выявить.

3.2 Легла ли запись в базу

После успешного POST проверьте в SQL-панели Supabase, что строка реально создана:

select id, slug, title, accent from shops where slug = 'test-qa-1';
select id, title, price_kop, stock, status from skus order by id desc limit 5;
  • Магазин появился в shops с верными slug, brand, accent
  • Привязки в infra_bindings созданы (участник, фулфилмент)
  • Товар появился в skus со статусом ACTIVE и ценой в копейках
  • Повторный POST того же slug — отклонён (уникальность), а не создаёт дубль
  • Цена хранится в копейках (price_kop), не в рублях
Проверка на дубль — критична. Форма проверяет уникальность slug на клиенте, но защита должна быть и в базе (UNIQUE-ограничение). Два POST с одним slug должны дать одну запись, второй — ошибку. Если создаются две — это баг схемы, не формы.

Уровень 4 — сквозной путь и приёмка на людях

4.1 Сквозной сценарий (вы)

Пройдите весь путь селлера как единую цепочку, не по частям:

  1. Shop Form → создать магазин test-e2e → подтвердить, что вернулся успех
  2. Перейти по ссылке в SKU-CRUD → добавить 3 товара (один через фото, два через CSV)
  3. Открыть витрину магазина (система.рф/shop/test-e2e или прототип) → товары видны, цены и бренд-цвет совпадают
  4. Открыть агента Системы → спросить товар этой категории → товар в выдаче с меткой 🟢
  5. Отредактировать цену в SKU-CRUD → обновить витрину → цена изменилась
  6. Перевести товар в DRAFT → на витрине и у агента он исчезает
Это и есть главный тест. Он проверяет инвариант всей системы: «wizard создаёт данные, витрина и агент их показывают, все — клиенты одного API». Если товар, добавленный в SKU-CRUD, появляется на витрине и у агента и исчезает при DRAFT — цепочка селлера работает целиком.

4.2 Приёмка на живых селлерах (UAT)

2–3 реальных пекаря (кандидаты Масса Матере и знакомые селлеры) проходят путь сами, без подсказок, вы наблюдаете и засекаете:

  • Время до первого товара — цель по спецификации: магазин 10 мин + импорт 10–30 мин
  • Где застряли — какой шаг вызвал вопрос или паузу (это точки drop-off)
  • Что заполнили неверно — если поле понимают не так, как задумано, — это дефект формулировки
  • Дошли ли до «товар в витрине» без помощи — критерий успеха онбординга
Критический шаг — импорт товаров. По спецификации именно шаг 4 даёт больше всего drop-off. На UAT смотрите на него пристальнее всего: если пекарь не смог за 30 минут завести каталог — это блокер запуска, а не косметика.

Критерий готовности

Путь селлера считается протестированным и готовым к расширению (живая витрина, каналы), когда:

  • Уровень 1 — 22/22 автопроверок зелёные выполнено
  • Уровень 2 — оба чек-листа пройдены в Chrome и на телефоне без ошибок в Console
  • Уровень 3 — все три маршрута существуют, запись реально ложится в shops и skus, дубль slug отклоняется
  • Уровень 4 — сквозной сценарий проходит целиком (товар доходит до витрины и агента), и хотя бы 2 из 3 селлеров на UAT дошли до товара в витрине без помощи
  • Все дефекты приоритета P0–P1 закрыты; P2–P3 — либо закрыты, либо внесены в бэклог осознанно
Порядок, а не всё сразу. Уровни идут по возрастанию стоимости: не зовите селлеров на UAT (уровень 4), пока не убедились, что API вообще пишет в базу (уровень 3). Иначе потратите живых людей на баг, который ловится одним curl.
