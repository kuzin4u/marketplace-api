1. Pipeline формирования каталога SKU

SKU проходит 6 стадий от создания до появления в каталоге Системы.

1
Создание. Селлер в ЛК (или через API) создаёт карточку: title, description, фото, цена, сток, категория, теги, вес, размеры, зоны доставки. Статус = DRAFT.
↓
2
Авто-валидация. Marketplace Service проверяет обязательные поля, формат фото (≥1, ≥800px), уникальность (нет дубля title+seller), корректность категории, цена > 0, сток ≥ 0. Не прошло → ошибка 422, не сохраняется.
↓
3
Авто-модерация (ML). Проверка фото (NSFW-фильтр, качество), проверка текста (запрещённый контент, спам-слова, завышенные обещания). Pass → статус ACTIVE. Fail → статус MODERATION, в очередь ручной проверки.
↓
4
Ручная модерация (если ML не уверен или первые 3 SKU нового селлера). Модератор: approve → ACTIVE, reject → REJECTED с причиной. SLA: 4ч рабочего времени.
↓
5
Запись в PostgreSQL. Статус ACTIVE → SKU доступен в магазине селлера (visible_shop=true). Если visible_catalog=true → переход к шагу 6.
↓
6
Индексация в Elasticsearch. CDC (Debezium → Kafka → ES consumer) подхватывает INSERT/UPDATE. Задержка < 5 сек. SKU появляется в поиске каталога Системы.
ЖИЗНЕННЫЙ ЦИКЛ СТАТУСА SKU ┌──────────────────────────────────────────────┐ │ │ Селлер создаёт │ ▼ ──────────→ DRAFT ──→ валидация OK ──→ ML OK ──→ ACTIVE ──→ [в каталоге] │ │ │ │ ML не уверен │ селлер архивирует │ │ ▼ │ MODERATION ARCHIVED │ │ │ │ approve reject │ │ │ │ ▼ ▼ │ ACTIVE REJECTED │ │ │ селлер исправляет │ │ └──────────────────────────────┘ Триггеры выхода из ACTIVE: · stock = 0 → OUT_OF_STOCK (автоматически) · stock > 0 снова → ACTIVE (автоматически) · селлер скрывает → ARCHIVED · модератор блокирует → BLOCKED · seller suspended → все SKU → SUSPENDED

1.2 Категории и таксономия

Дерево категорий — единое для каталога и для всех магазинов. Селлер выбирает категорию при создании SKU. Организатор управляет деревом.

ДЕРЕВО КАТЕГОРИЙ (стартовое, Волна 0–1) categories (tree, parent_id → self) ├── Продукты питания │ ├── Хлеб и выпечка ← Масса Матере, Пекарня Сергеева │ ├── Кондитерские изделия ← торты, пирожные │ ├── Молочные продукты ← Ферма Кузнецова │ ├── Мясо и птица │ ├── Овощи и фрукты │ ├── Мёд и варенье │ └── Напитки ├── Крафт и handmade │ ├── Косметика │ ├── Свечи и ароматы │ ├── Керамика │ └── Текстиль ├── Фермерские товары │ ├── Молоко и сыры │ ├── Яйца │ ├── Масла │ └── Крупы и зерно └── Товары для дома (Волна 2 — расширение) ├── DIY └── Автотовары Правила: · Максимальная глубина: 3 уровня · Селлер выбирает leaf-категорию (самый нижний уровень) · Один SKU = одна категория (основная) + теги (вспомогательные) · ML-подсказка при создании: «Похоже на категорию: Хлеб и выпечка» · Организатор добавляет/перемещает категории без влияния на SKU (SKU привязан к ID, не к позиции в дереве)

1.3 Индексация SKU в Elasticsearch

CDC PIPELINE: PostgreSQL → Elasticsearch PostgreSQL (skus table) │ │ WAL (Write-Ahead Log) ▼ Debezium (CDC connector) │ Captures: INSERT, UPDATE, DELETE │ Filters: status IN ('ACTIVE', 'OUT_OF_STOCK') │ AND visible_catalog = true ▼ Kafka (topic: skus.catalog.changes) │ Partitioned by seller_id │ Retention: 7 days ▼ ES Consumer (Node.js worker) │ ├── INSERT/UPDATE (status=ACTIVE, visible_catalog=true) │ → ES upsert: PUT /sku_catalog/_doc/{sku_id} │ ├── UPDATE (status≠ACTIVE OR visible_catalog=false) │ → ES delete: DELETE /sku_catalog/_doc/{sku_id} │ ├── DELETE │ → ES delete │ └── Enrichment при upsert: · JOIN shops → seller_name, seller_slug, seller_rating · JOIN categories → category_path, category_slug · JOIN registry.participants → seller_group, seller_joined_at · Compute: popularity_score = log(orders_count+1) * rating ▼ Elasticsearch (index: sku_catalog) │ │ Задержка end-to-end: < 5 секунд │ Мониторинг: consumer lag alert > 30 сек ▼ Доступен в каталоге Системы ЧТО НЕ ПОПАДАЕТ В ES (и значит, не видно в каталоге): · status = DRAFT, MODERATION, REJECTED, BLOCKED, SUSPENDED · visible_catalog = false (селлер скрыл из каталога) · seller.status ≠ ACTIVE (селлер приостановлен/вышел) · stock = 0 И stock_reserved = 0 (нет даже резерва)

2. Pipeline формирования каталога магазинов

Магазин создаётся как побочный эффект регистрации селлера в Системе. Нет отдельного «создания магазина» — есть вступление участника.

1
Заявка. Будущий селлер подаёт заявку: ИНН, тип (ФЛ/ИП/ООО), описание бизнеса, категории товаров, регион. Через WebApp (08) или по приглашению.
↓
2
KYC. Auth Service (03): проверка ИНН через ФНС, ЕСИА (если ФЛ), проверка ОГРН (если ЮЛ). Результат: KYC Level 1 (ИНН) или Level 2 (ЕСИА).
↓
3
Проверка гейта (ст. 13.2). Registry Service (10): есть ли ≥2 в каждой ключевой роли (фулфилмент, логистика, банк)? Если нет — селлер встаёт в очередь ожидания.
↓
4
Приёмка в реестр (ст. 4.3). Registry Service: создаёт participant (role=SELLER), присваивает PTR-id, регион, начальный рейтинг, группу (1/2/3).
↓
5
Договор присоединения. Contract Builder (07): генерирует договор + SLA-соглашение. Подписание КЭП (или ПЭП для ФЛ). После подписания: participant.status = ACTIVE.
↓
6
Создание магазина. Marketplace Service (11): createShop. Селлер настраивает бренд (логотип, цвет, обложка, описание), выбирает slug, включает каналы. Магазин появляется по URL /shop/{slug}.
↓
7
Индексация в каталог магазинов. Магазин появляется в /catalog/shops (листинг всех магазинов Системы). CDC → ES index: shops_catalog.
Пороговый ввод (ст. 13.4): Массовый приём гр. 3 («Новые») открывается при достижении общей базой порогового размера. До этого — только гр. 1 и гр. 2 по приглашению.

2.2 Рейтинг магазина: формирование

Рейтинг не задаётся вручную. Формируется Системой по метрикам исполнения (ст. 4.3).

КОМПОНЕНТЫ РЕЙТИНГА МАГАЗИНА shop_rating = weighted_avg( w1 × review_avg, // средняя оценка покупателей (1–5) w2 × fulfillment_rate, // % заказов доставленных в срок w3 × dispute_rate_inv, // 1 − (споры / заказы) w4 × response_rate, // % отзывов с ответом селлера w5 × freshness // регулярность обновлений ) Веса (стартовые, настраиваемые Организатором): w1 = 0.40 (отзывы покупателей — главный сигнал) w2 = 0.25 (исполнительская дисциплина) w3 = 0.20 (отсутствие проблем) w4 = 0.10 (вовлечённость селлера) w5 = 0.05 (активность) Пример: Масса Матере: review_avg = 4.8 × 0.40 = 1.92 fulfillment = 0.96 × 0.40 × 5 = 1.20 (нормализация к 5) dispute_inv = 0.98 × 0.20 × 5 = 0.98 response = 0.80 × 0.10 × 5 = 0.40 freshness = 0.90 × 0.05 × 5 = 0.23 ───────────────────────────────── shop_rating = 4.73 → отображается ⭐ 4.7 Обновление: ежедневно (02:00 МСК), cron job Минимум для рейтинга: ≥ 5 отзывов (до этого — «Новый магазин») Decay: отзывы старше 180 дней → вес × 0.5

3. Ранжирование SKU в выдаче каталога

Определяет порядок товаров в результатах поиска и в категориях каталога. Работает через Elasticsearch function_score.

ФОРМУЛА РАНЖИРОВАНИЯ SKU final_score = text_relevance × quality_score × commercial_score × freshness_score × geo_score × policy_score ═══════════════════════════════════════════════════════════════ quality_score = (1 + 0.15 × log(1 + rating)) × (1 + 0.08 × log(1 + reviews_count)) × (1 + 0.05 × log(1 + seller_rating)) Что делает: товары с высоким рейтингом и большим числом отзывов поднимаются. seller_rating — доверие к магазину. ═══════════════════════════════════════════════════════════════ commercial_score = (1 + 0.10 × log(1 + orders_count)) × (1 + 0.12 × conversion_rate) Что делает: товары, которые реально покупают (не просто смотрят), поднимаются. Conversion = orders / views за 30д. ═══════════════════════════════════════════════════════════════ freshness_score = max(0.7, 1 − 0.01 × days_since_update) Что делает: товары, обновлённые недавно, получают буст. Старые (>30 дней без обновлений) теряют до 30% score. Floor = 0.7 — старый товар не пропадает совсем. ═══════════════════════════════════════════════════════════════ geo_score = max(0.5, 1 − 0.003 × distance_km) Что делает: товар со склада ближе к покупателю — выше. Работает только при известной геолокации покупателя. Floor = 0.5 — дальний товар не пропадает. ═══════════════════════════════════════════════════════════════ policy_score (ст. 11.2, priority_boost) if seller_group == 2 AND days_since_join < 90: policy_score = 1.30 // +30% для «Разочаровавшихся» elif seller_group == 3 AND days_since_join < 30: policy_score = 1.10 // +10% для «Новых» (мягкий буст) else: policy_score = 1.00 // без буста Что делает: временный бонус для новых селлеров. Гр. 2: +30% на 90 дней (стимул быстрого старта). Гр. 3: +10% на 30 дней (видимость без перекоса). ТОЛЬКО из сетевого притока (каталог). В магазине — не работает.

3.1 Ранжирование магазинов в выдаче /catalog/shops

Аналогичная формула, но для магазинов. Покупатель ищет «пекарня» или «молочные продукты» → ранжированный список магазинов.

GMV нормализуется делением на 10K. ═══════════════════════════════════════════════════════════════ policy_score (для магазинов) if seller_group == 2 AND days_since_join < 90: return 1.25 // +25% для «Разочаровавшихся» elif seller_group == 3 AND days_since_join < 30: return 1.10 // +10% для «Новых» else: return 1.00 Чуть ниже чем для SKU (1.25 vs 1.30) — магазин ранжируется по совокупности, не по отдельному товару.

3.2 Настройка весов ранжирования

Организатор настраивает ВЕСА формулы, не позиции конкретных SKU. Ручное продвижение запрещено.

ADMIN API: /api/v1/admin/marketplace/ranking-config { "sku_ranking": { "quality_weights": { "rating_factor": 0.15, // вес рейтинга товара "reviews_factor": 0.08, // вес числа отзывов "seller_rating_factor": 0.05 // вес рейтинга магазина }, "commercial_weights": { "orders_factor": 0.10, // вес числа заказов "conversion_factor": 0.12 // вес конверсии }, "freshness": { "scale_days": 30, // за сколько дней decay "floor": 0.7 // минимальный множитель }, "geo": { "scale_km": 50, // масштаб геодистанции "floor": 0.5 }, "policy": { "group2_boost": 1.30, // буст гр.2 "group2_days": 90, // период буста гр.2 "group3_boost": 1.10, // буст гр.3 "group3_days": 30 // период буста гр.3 } }, "shop_ranking": { "reputation_factor": 0.20, "activity_orders_factor": 0.10, "activity_sku_factor": 0.05, "activity_gmv_factor": 0.08, "policy": { "group2_boost": 1.25, "group2_days": 90, "group3_boost": 1.10, "group3_days": 30 } } } Кто меняет: ADMIN или ORGANIZER (role check) Где хранится: PostgreSQL (config table) + Redis cache (5 мин TTL) Audit: Каждое изменение → audit_log (кто, когда, старое→новое) A/B тест: Можно запустить два набора весов параллельно (50/50)
Запрет ручного продвижения. Организатор НЕ может вручную поднять конкретный SKU или магазин в выдаче. Только настройка формулы, которая применяется одинаково ко всем. Это защищает доверие участников: каждый конкурирует по общим правилам (ст. 10.1).
