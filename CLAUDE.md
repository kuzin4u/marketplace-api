# ПТК — программно-технический комплекс распределённого маркетплейса

Бэкенд Системы: витрины селлеров, каталог, заказы, эскроу-клиринг, агентный слой.
Node/Express + PostgreSQL. Язык работы и комментариев — русский.

**Главный принцип проекта:** нормы первичны, код вторичен. Каждая таблица и каждый
маршрут привязаны к статье «Правил системы ред.3». Если правка кода противоречит
статье — правка неверна, а не статья. Раздел 3 ниже перечисляет нормы, которые
нельзя нарушать ни при каких обстоятельствах.

## 1. База данных

### Инфраструктура

| Параметр | Значение |
|---|---|
| Текущая площадка | Supabase (управляемый PostgreSQL 16) |
| Подключение | **pooler, transaction mode, порт 6543** — не direct |
| Переменная | `DATABASE_URL` (в env Render, локально в `.env`) |
| SSL | пул `pg` с `ssl: { rejectUnauthorized: false }` |
| Хостинг API | Render, free tier, Frankfurt — холодный старт ~30 сек после простоя |

URL для direct и pooler **различаются**. При ошибке подключения первым делом
проверять, что взят именно pooler-URL, а не direct.

**Планируемая миграция:** боевая база уходит на Yandex Cloud (управляемый
PostgreSQL). Причина — требование российской юрисдикции: первичная запись
персональных данных должна быть в РФ, Supabase этому не удовлетворяет.
Не завязывать код на специфику Supabase (PostgREST, Supabase-клиент, RLS-политики
через их панель) — только чистый PostgreSQL через `pg`.

### Соглашения по идентификаторам

Все первичные ключи — строки с типовым префиксом, генерируются хелпером `genId`:

```
PTR-<hex8>     participants   — участник (селлер, 3PL, курьер, организатор)
SHOP-<slug>    shops          — id магазина собирается ИЗ slug, не случайный
SKU-<hex8>     skus
ORD-<hex8>     orders
CUST-<hex8>    customers
CAT-<UPPER>    categories     — фиксированный справочник, см. ниже
```

### Ключевые таблицы

Базовый контур: `participants`, `participant_tariffs`, `shops`, `skus`,
`categories`, `orders`, `order_items`, `clearing_splits`, `customers`,
`customer_bindings`, `infra_bindings`, `audit_log`, `seller_auth`.

Агентный слой (миграция `05_agent_layer.sql`): реестр агентов, мандаты, журнал
согласий, веса выдачи, учёт потребления — 13 таблиц + 5 view.

Конфигуратор каналов (`01_alpha_channels.sql`): `channels`,
`fulfilment_services`, `visibility_rules`, `fulfilment_rules`,
`settlement_rules`, `ratchet_log`.

### Грабли схемы — проверять при каждом обращении

| Что | Как на самом деле |
|---|---|
| `skus.price` | **в рублях**, не в копейках. Формы держат копейки внутри и делят на 100 при отправке |
| `orders.total_amount` | колонка называется так. `o.total` не существует — из-за этого smoke-test отдаёт 500 (расхождение Р6) |
| `participants.seller_group` | **integer**, не буква. `'A'` даёт `invalid input syntax for type integer` |
| `skus.category_id` | только реальный id из справочника. Выдуманная строка `'bread'` даёт 500 |
| `participants.inn`, `.name` | обязательные |
| Видимость товара | две независимые оси: `visible_shop` (витрина селлера) и `visible_catalog` (каталог Системы и агент) |
| `moderation_status` | по умолчанию `PENDING`, модель publish-first |

**Справочник категорий (7, закрытый):** `CAT-FOOD`, `CAT-BREAD`, `CAT-PASTRY`,
`CAT-CRAFT`, `CAT-DAIRY`, `CAT-HOME`, `CAT-FARM`.
Фронт обязан тянуть его живьём из `GET /api/v1/catalog/categories`; хардкод
допустим только как офлайн-резерв.

### Открытый долг по базе

- **RLS не включён** на базовых таблицах. В `customers` лежат данные покупателей,
  а таблицы `public` видны через PostgREST по anon-ключу. Закрыть до боевого
  запуска. В агентном слое RLS FORCE уже есть — брать за образец.

## 2. Соглашения по API

### Структура

- Все прикладные маршруты — на префиксе **`/api/v1/*`**.
- Единственное исключение: **`/api/health`** без версии.
- Основной файл — `server.js` (~1100 строк). Модули монтируются в нём же,
  строки 45–47.

### Модульный стиль

Модуль экспортирует фабрику, принимающую `app` и общие хелперы:

```js
const { requireSeller } = require('./auth-seller')(app, { db, dbOne, genId });
```

Смонтированы: `auth-seller`, `channels-api`, `customers-api`.
Новый модуль писать в этом же стиле — не заводить собственный пул соединений,
собственный генератор id и собственный формат ошибок.

Хелперы: `db()` возвращает `rows`, `dbOne()` — первую строку.

### Авторизация — критично

Проект финтех с эскроу. Подменённый `seller_id` = выплата не тому человеку.

- `seller_id` берётся **только из JWT**: `req.seller_id` после `requireSeller`.
- Никогда — из тела запроса или из пути URL.
- Токен: заголовок `Authorization: Bearer`, TTL 12 часов, секрет из `JWT_SECRET`.
- На запись в чужой магазин — `assertShopOwner` на каждой операции.
- Модуль без выданного `requireSeller` отвечает **501**, а не работает открыто
  (fail-closed). Это правильное поведение, не баг.
- Чекаут идемпотентен по заголовку `Idempotency-Key`.

**Незакрытая дыра (Р1, высший приоритет):** маршруты
`/seller/:seller_id/products` (GET/POST/PATCH) и `/seller/:seller_id/stats`
до сих пор без `requireSeller`, `seller_id` читается из URL — в коде висит
комментарий «no JWT yet». Любая работа рядом с этими маршрутами должна
заканчиваться врезкой `requireSeller` и удалением `:seller_id` из пути.

**Р2, ещё выше по срочности:** `JWT_SECRET` имеет дефолт
`'DEV-ONLY-CHANGE-ME'`. Если переменная не задана в окружении, защита обнуляется
молча, без ошибки. Проверять наличие переменной при старте и падать, если её нет.

### Коды ответов

| Код | Когда |
|---|---|
| 401 | нет токена / неверный логин-пароль (ответ одинаковый в обоих случаях — не подсказывать, существует ли логин) |
| 403 | токен есть, но роль не SELLER, либо чужой магазин |
| 409 | `NOT_ENOUGH_STOCK` при резерве; понижение уровня сервиса (храповик) |
| 501 | модуль смонтирован без авторизации |

### Правила изменений

- Суммы заказа считает **сервер**. Клиент присылает только `items[{sku_id, qty}]`
  и `entry_point` — присланной сумме не доверять.
- Тарифы живут строками в `participant_tariffs` со сроком действия. Переход
  0,2% → 0,5% — это вставка строки, **не правка кода**. Никаких ставок в
  константах.
- CORS сейчас открыт всем (Р7) — сузить при работе рядом.
- Локальной копии репозитория на машине нет: правки идут через веб-интерфейс
  GitHub в `marketplace-api`, коммит в `main`, Render автодеплоит ~2 мин.

### Порядок закрытия расхождений

Зафиксирован аудитом: **Р2 → Р1 → Р6 → Р3 → Р4 → Р5**.
Р3 — конфигуратор каналов не влияет на выдачу (`effective_channels` не
вызывается ни разу, витрина фильтрует по `visible_*` — два источника истины).
Р4 — `take_rate` канала не доходит до клиринга. Р5 — `settlement mode`
пишется, но `POST /orders` его не читает.

## 3. Требования Правил ред.3

Единый документ: преамбула 0.1–0.8 + статьи 1–21. При расхождении любого
документа пула с Правилами норма — Правила.

### Нормы, вшитые в базу как CHECK и триггеры — не снимать

| Норма | Статья | Механизм |
|---|---|---|
| Место в выдаче не продаётся | ст.19 | `paid_placement = FALSE`, поля платного места в схеме нет вообще |
| Исполнение весит не меньше цены | ст.19 | `CHECK w_execution >= w_price` |
| Доход не берётся процентом с оборота | ст.20 | `basis IN ('FIXED','TIERED','PER_UNIT')` — процент невыразим |
| Журнал согласий неизменяем | ст.15 | запрет `UPDATE`/`DELETE` + хэш-цепочка |
| Храповик только вверх | конфигуратор | `CHECK to_level > from_level`, понижение = 409 |

Если задача требует обойти любое из этих ограничений — это сигнал, что задача
поставлена неверно. Остановиться и сказать об этом, а не снимать CHECK.

### Нормы, которые держатся отсутствием механизма

- **Формула ранжирования (ст.11.3)** живёт в SQL:
  `score = (1 + 0,15·ln(1+rating)) · (1 + 0,08·ln(1+reviews)) · (1 + 0,10·ln(1+orders))`,
  буст группы 2 = 1,3 на 90 дней, группы 3 = 1,1 на 30 дней.
  **Цена в формуле не участвует.** Не добавлять — это и есть соблюдение ст.19.

- **Расчёты только через контур Системы (ст.20).** Допустимы СБП, эквайринг,
  эскроу. Цифровая валюта запрещена. п.20.8: перечень средств платежа задан для
  юрисдикции РФ; в иной юрисдикции его определяет Организатор, сохраняя эскроу
  и запрет крипты.

- **Три «нельзя» оргструктуры:** допуск ≠ выдача; партнёрства ≠ ранжирование;
  расчёты ≠ правила сплита. Не смешивать эти контуры в одном модуле.

- **Организатор — казначей, не бенефициар (ст.7).** Доход идёт из расчётов и
  финансовых потоков, а не налогом с участников. Потолок совокупного удержания
  с селлера — около 15% GMV.

### Источник сделки

`source_type` принимает `MIGRATED` / `NETWORK` / `AGENT` (ст.10.4, ст.18).
Маппинг в `POST /orders`: `entry_point = SHOP` → `MIGRATED`;
`CATALOG` и `REFERRAL_SYSTEM` → `NETWORK`.
Товар — атом (ст.9.4), source-of-truth в PostgreSQL.

### Клиринг

Сплит по ролям, сумма долей обязана сходиться с `total_amount`:

```
FULFILLMENT = тариф ASSEMBLY × Σqty
LOGISTICS   = тариф зоны из delivery
ORGANIZER   = % × total_goods   (ставка строкой из participant_tariffs)
SELLER      = остаток
```

Эталон для проверки, заказ ORD-00001:
SELLER 817,16 / FULFILLMENT 600 / LOGISTICS 350 / ORGANIZER 2,84.

### Разделение контуров агентного слоя (ст.16)

Три ключа с разными правами: `RUNTIME`, `ADMISSION`, `READONLY`.
Уровень агента определяется по реестру через заголовок `X-Agent-Code` —
**не из тела запроса**. Агент селлера со статусом `MIGRATED` каталог рынка
не получает.

## 4. Как работать над задачами

- Проверять гипотезы о схеме **запросом к базе**, а не по документации: пул
  документов местами отстаёт от кода, и наоборот. Живой прогон уже трижды
  вскрывал расхождения (seller_group, category_id, total_amount).
- Не создавать модули, дублирующие существующие маршруты, — сначала прочитать
  `server.js` целиком и убедиться, что маршрута действительно нет.
- Тесты: уровень L1 (логика, jsdom) держать зелёным, при правке форм
  перепрогонять `test-forms.js` и `test-forms-extended.js`.
- Деливери документации — интерактивный HTML в стиле пула (IBM Plex),
  двусторонние ссылки между документами, проверка целостности пула после правки.
- Решения, принятые в текущей сессии, старше документации: если пользователь
  сказал иначе, чем написано в файле пула, — прав пользователь.
