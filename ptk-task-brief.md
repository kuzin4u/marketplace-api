# Задание на разработку и развёртывание ПТК

Проект: «Распределённый маркетплейс», программно-технический комплекс.
Репозиторий: `marketplace-api`. Документ читается вместе с `CLAUDE.md`.

Назначение файла: очередь работ для Claude Code. Каждый пакет — отдельная
сессия с готовым промптом, критерием приёмки и правкой в пул документов.
Пакеты идут строго по порядку: каждый следующий опирается на закрытый предыдущий.

---

## 0. Рамка

### Что уже построено

Схема PostgreSQL с привязкой таблиц к статьям Правил; `server.js` (~1100 строк,
26 маршрутов); три смонтированных модуля (`auth-seller`, `channels-api`,
`customers-api`); агентный слой (13 таблиц + 5 view, нормы вшиты в CHECK);
конфигуратор каналов с храповиком; формы пути селлера; живая витрина, читающая
реальный API; сквозная цепочка селлер → магазин → товар → витрина проверена
вживую. Пул — 74 HTML, связаны двусторонними ссылками.

### Что задание закрывает

Трек A (витрина и расчёты без банковского эскроу) доводится до боевого
состояния: закрываются восемь расхождений аудита, включается защита
персональных данных, устраняется раздвоение источников истины.

### Что задание НЕ закрывает и почему

| Блокер | Суть | Что требуется от вас |
|---|---|---|
| **Б1. Норма** | В Правилах ред.3 ст.1–13 стоят слотами «перенос из ред.2», текст не перенесён; заголовок ст.5 неизвестен; не решены порог T2I и держатель журнала согласий | Загрузить файл ред.2 и принять два открытых решения. До этого агент не может сверять код со статьями 1–13 |
| **Б2. Площадка** | Боевая база должна быть в юрисдикции РФ; Yandex Cloud принят предварительно | Зафиксировать площадку. Процедура развёртывания (П9) пишется под конкретную |
| **Б3. Банк** | Расчётный Банк R1–R14 не выбран; реальной оплаты нет, сделка останавливается на PENDING | Выбор банка. До этого полный цикл не разворачивается ни при каком качестве кода |

### Три решения, которых ждут пакеты

- **Р3, источник истины видимости.** Сейчас витрина фильтрует по
  `skus.visible_shop`/`visible_catalog`, а конфигуратор каналов ведёт
  собственные правила, и `effective_channels` не вызывается ни разу. Нужен один
  источник. Рекомендация — резолвер конфигуратора, а `visible_*` становится
  его производной. Требуется ваше подтверждение (пакет П5).
- **Р5, механизм расчёта Масса Мадре.** Из трёх показанных схем (всегда через
  Систему / выбор на каждый заказ / fulfilment отдельно) выбор не сделан. Пакет
  П7 без него не стартует.
- **Кабинет заказов.** Свести поток прямых продаж и поток Системы в один
  `cabinet-orders` или развести — вопрос открыт (пакет П9).

### Правила работы для агента (общие для всех пакетов)

1. Гипотезу о схеме проверять запросом к базе, а не по документу.
2. Не создавать модуль, дублирующий существующий маршрут: сначала прочитать
   `server.js` целиком.
3. Ограничения CHECK и триггеры, реализующие нормы, не снимать. Если задача
   требует их обойти — остановиться и сказать об этом.
4. После каждого пакета обновлять указанные документы пула и проверять
   целостность двусторонних ссылок.
5. Деплой не выполнять самостоятельно: готовить диф, выкладку делает человек
   (`git push` в `main` = автодеплой Render в бой).

## Пакет П2 — Р1: кабинет селлера закрыт

**Промпт:**

```
Маршруты /seller/:seller_id/products (GET, POST, PATCH) и
/seller/:seller_id/stats работают без requireSeller, seller_id берётся из URL —
```

## Пакет П5 — Р3: один источник истины видимости

**Требует решения по источнику (см. раздел 0).**

**Промпт:**

```
Витрина и каталог фильтруют товары по skus.visible_shop / visible_catalog, а
конфигуратор каналов ведёт visibility_rules с приоритетом SKU > CATEGORY > SHOP,
и функция effective_channels не вызывается в server.js ни разу. Два источника
истины. Сделай источником резолвер конфигуратора: маршруты витрины и каталога
спрашивают effective_channels, поля visible_* становятся производной и
пересчитываются при изменении правил. Не ломай существующие ответы API —
контракт для фронта остаётся прежним.
```

**Приёмка:** тумблер в дашборде каналов меняет реальную выдачу витрины;
тест-кейс Масса Мадре (три схемы на трёх категориях) отрабатывает; храповик
по-прежнему запрещает понижение.

**Пул:** `sku-visibility-seller.html`, `alpha-channels-dashboard.html`,
`vitrina-creation-components.html` — снять пометки «читает, не пишет».

## Пакет П6 — Р4: take_rate доходит до клиринга

**Промпт:**

```
Сплит в POST /orders берёт единый ORGANIZER_FEE, а take_rate канала из
конфигуратора до клиринга не доходит. Проведи ставку канала в расчёт сплита.
Сохрани инварианты: ставка берётся строкой из participant_tariffs с проверкой
срока, а не константой в коде; сумма сплитов равна total_amount; формула
FULFILLMENT/LOGISTICS/ORGANIZER/SELLER не меняется по структуре. Прогони
эталон ORD-00001: SELLER 817.16 / FULFILLMENT 600 / LOGISTICS 350 /
ORGANIZER 2.84.
```

**Приёмка:** эталон сходится; заказ через канал с иной ставкой даёт иной сплит,
сумма по-прежнему равна `total_amount`; смена ставки — вставка строки, кода не
касается.

**Пул:** документы по клирингу, раздел расхождений.

## Пакет П7 — Р5: режим расчёта в заказе

**Требует выбора механизма (см. раздел 0).**

**Промпт (шаблон, механизм подставить):**

```
settlement mode (OWN / SYSTEM / PER_ORDER) пишется в settlement_rules, но
POST /orders его не читает — из трёх механизмов Масса Мадре работает только
«всегда через Систему». Реализуй механизм <НОМЕР>. Заказ при создании
определяет режим расчёта через резолвер и записывает его в orders. Эскроу
остаётся обязательным для режима SYSTEM. Цифровая валюта не поддерживается ни в
каком режиме (ст.20).
```

**Приёмка:** заказ несёт режим расчёта; режим SYSTEM идёт в эскроу-контур;
режим OWN не попадает в клиринг Системы; переключение не ломает существующие
заказы.

**Пул:** `massamadre-settlement-mechanisms.html` — выбранный механизм помечается
принятым, два других остаются как рассмотренные варианты.

## Порядок и зависимости

```
П0 инвентаризация
 └─ П1 секрет ──┐
    П2 кабинет ─┼─ безопасность, идут подряд
    П4 RLS ─────┘
    П3 smoke-test (независим, можно параллельно)
       └─ П5 источник истины  ← требует решения
          └─ П6 take_rate
             └─ П7 режим расчёта  ← требует выбора механизма
                └─ П8 периметр и агент
                   └─ П9 тесты и развёртывание  ← требует площадки
```

Блокеры Б1 и Б3 лежат вне этой очереди: без нормы ст.1–13 нельзя завершить
сверку кода с Правилами, без банка — запустить реальную оплату. Оба пакета
работ начинаются с вашего решения, а не с сессии Claude Code.
