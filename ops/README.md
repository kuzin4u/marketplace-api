# ops

Скрипты эксплуатации: то, что запускают руками при переносе, проверке
и обслуживании. Не участвует в работе приложения — `api/server.js` ничего
отсюда не импортирует, и удаление любого файла не ломает деплой.

## Сейчас

| Файл | Когда нужен |
|---|---|
| `code-map.tsv` | реестр соответствия документов пула и кода. Источник правды |
| `render-code-map.py` | собирает реестр в HTML-страницу для пула |
| `smoke.sh` | проверка контура одной командой против любого адреса |
| `check-supabase.sql` | диагностика базы перед переносом: RLS, расширения, счётчики |
| `dump-restore-verify.sh` | дамп, восстановление в Postgres в Docker, сверка |

```bash
python3 ops/render-code-map.py          # пересобрать реестр
bash ops/smoke.sh                       # проверить localhost:3000
bash ops/smoke.sh https://marketplace-api-ujfh.onrender.com
```

`smoke.sh` возвращает 0, если всё прошло, — годится для автоматической
проверки после деплоя. Отдельно проверяет, что запись без токена
отбивается: если этот пункт зелёный, авторизация записи работает.

### Что smoke.sh покажет после миграции 04

Миграция переименовала денежные поля и убрала `seller_id` из заказа.
Маршруты витрины и каталога это не затрагивает, но если после применения
04 в проверке начнут падать пункты «товары магазина» или «поиск» —
причина в коде, который всё ещё просит `price`. Правится в задаче 0.3.

## Схема живёт не здесь

Файлы схемы и миграции лежат в `schema/`, а не в `ops/`: они меняют
данные, а не обслуживают их. Порядок применения:

```
schema/01_schema.sql                 базовая схема, 13 таблиц
seed/02_seed_massamadre.sql          пилот
schema/03_integrity.sql              шесть ограничений целостности
schema/04_suborders_consents.sql     задача 0.1: подзаказы, согласия, копейки
```

`03` обратима — ограничения снимаются. `04` необратима: колонки удалены,
суммы пересчитаны, откат только восстановлением из копии. Перед её
применением на боевой базе прогоняется `dump-restore-verify.sh`.

## Появится

Порядок соответствует задачам плана реализации, редакция 3.

| Файл | Задача | Что делает |
|---|---|---|
| `sheets-export.py` | 0.7 | выгрузка пилота из Google Sheets в промежуточный формат |
| `sheets-import.sql` | 0.7 | загрузка в схему: заказ становится родительским с одним подзаказом, история помечается признаком «до введения согласий» |
| `reconcile.sql` | 0.8 | семь ежедневных сверок: состав, суммы, остатки, статусы, покупатели, клиринг, редкие пути |
| `reconcile-report.sh` | 0.8 | прогон сверок, отчёт, счётчик чистых суток |
| `pg-backup.sh` | 0.0 | регулярный дамп с ротацией |
| `restore-drill.sh` | 0.0 | учебное восстановление из копии — приёмочный критерий площадки |

Загрузчик истории обязан объявить себя переносом, иначе миграция 04
не даст поставить признак «до введения согласий»:

```sql
SET LOCAL app.history_migration = 'on';
```

## Чего здесь быть не должно

**Секретов.** Репозиторий публичный, и `ops/` попадает в GitHub Pages вместе
с остальным. Пароли, строки подключения, ключи — только в переменных окружения
и в хранилище секретов.

**Дампов и их производных.** `dump-restore-verify.sh` создаёт файл
с персональными данными покупателей. Маски в `.gitignore`:

```
*.dump
counts-*.txt
diff-*.txt
restore-*.log
code-map.html
```

**Кода приложения.** Модули API живут в `api/`. Если скрипт понадобился
серверу во время работы — он больше не эксплуатационный, его место в `api/`.

**Производного HTML.** `code-map.html` собирается генератором и в репозиторий
не коммитится: иначе появятся две версии, из которых одну будут править руками.
