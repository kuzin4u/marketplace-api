Роль в архитектуре ПТК

Marketplace Service — «лицо» Системы. Всё что видит покупатель (витрина, каталог, поиск) и селлер (магазин, SKU) проходит через этот сервис. Самый большой по объёму кода и самый нагруженный по трафику.

Каталог Системы: верхний уровень витрины (ст. 9.3)

КАТАЛОГ = ВСЕ SKU ВСЕХ СЕЛЛЕРОВ Условия попадания: sku.status = ACTIVE sku.visible_catalog = true sku.stock > 0 shop.status = ACTIVE Поиск (CatalogEngine): Спринт 0–2: PostgreSQL tsvector to_tsvector('russian', title || description) @@ plainto_tsquery('russian', 'хлеб на закваске') + индекс GIN Спринт 3+: Elasticsearch CDC (Debezium) → Kafka → ES consumer → ES index Задержка: PG insert → ES available < 5 сек ru_morph analyzer для русской морфологии function_score для ранжирования Фильтры: q — полнотекстовый поиск cat — категория (ID) price_min — мин. цена price_max — макс. цена rating_min — мин. рейтинг zone — зона доставки seller — конкретный селлер (для каталога магазина) sort — cheap|expensive|rating|new|relevance(default) Пагинация: page, limit (default 20, max 100) Ответ: { products, total, page, pages }

Ранжирование SKU (ст. 11.3)

ФОРМУЛА РАНЖИРОВАНИЯ final_score = relevance × quality × commercial × freshness × geo × policy Где: relevance = text match score (tsvector / ES BM25) Вес в запросе: title ×3, description ×1, tags ×2 quality = f(rating, reviews_count) = (1 + 0.15 × ln(1 + rating)) × (1 + 0.08 × ln(1 + reviews)) commercial = f(orders_count, conversion) = 1 + 0.10 × ln(1 + orders_count) freshness = f(created_at) = 1 + 0.05 × max(0, 30 - days_since_created) / 30 geo = f(buyer_zone, seller_zones) = 1.2 если зона совпадает, 1.0 иначе policy = priority_boost (ст. 11.3) = 1.3 если seller_group=2 И joined < 90 дней = 1.1 если seller_group=3 И joined < 30 дней = 1.0 иначе РЕАЛИЗАЦИЯ: Спринт 0–2 (PostgreSQL): ORDER BY ( (1 + 0.15 * ln(1 + rating)) * (1 + 0.08 * ln(1 + reviews_count)) * (1 + 0.10 * ln(1 + orders_count)) * CASE WHEN seller_group=2 AND joined > now()-'90d' THEN 1.3 WHEN seller_group=3 AND joined > now()-'30d' THEN 1.1 ELSE 1.0 END ) DESC Спринт 3+ (Elasticsearch): function_score { query: multi_match(q, [title^3, description, tags^2]) functions: [ {script_score: quality_formula}, {script_score: commercial_formula}, {gauss: {created_at: {origin:"now", scale:"30d"}}}, {script_score: policy_boost} ] score_mode: "multiply" } Антиманипуляция (ст. 11.6): • reviews: UNIQUE(order_id, sku_id) — один отзыв на заказ • orders: только COMPLETED считаются • Ручное продвижение: ЗАПРЕЩЕНО • Post-review: 5% случайная выборка

source_type: MIGRATED vs NETWORK (ст. 10)

ОПРЕДЕЛЕНИЕ SOURCE_TYPE entry_point → source_type ───────────────────────────────────── SHOP (/s/{slug}) → MIGRATED (клиент селлера) CHANNEL (TG-бот) → MIGRATED (клиент селлера) CATALOG (/catalog) → NETWORK (общее достояние) REFERRAL_SYSTEM → NETWORK (системная реферальная) REFERRAL_SELLER → MIGRATED (реферальная селлера) ФИКСАЦИЯ (ст. 10.5): Первый заказ покупателя у этого селлера фиксирует source_type. Все последующие заказы — тот же source_type (не пересчитывается). customer_bindings: { customer_id, seller_id, source_type, first_order_at } UNIQUE(customer_id, seller_id) ON CONFLICT: если binding уже есть → orders_count++, total_gmv+= Если нет → INSERT с source_type из entry_point ЧТО ЭТО ДАЁТ СЕЛЛЕРУ: ЛК → Покупатели → «20 migrated (ваша база) / 3 network (из каталога)» Защита (ст. 10.2): мигрировавшая база НЕ перераспределяется через каталог Системы. Покупатель привязан к первому source_type. КОРРЕКТИВ К4: priority_boost гр.2 действует только на NETWORK-приток. Не на мигрировавшую базу гр.1.

Модерация SKU (ст. 13.1.4)

PUBLISH-FIRST МОДЕРАЦИЯ SKU создан → ML-проверка (2–5 сек) confidence ≥ 0.85: moderation_status = AUTO_APPROVED visible_shop = true visible_catalog = true ← сразу в каталоге status = ACTIVE confidence 0.50–0.85: moderation_status = PENDING visible_shop = true ← виден в магазине visible_catalog = false ← не в каталоге до проверки status = ACTIVE → очередь на ручную модерацию (SLA 4ч) confidence < 0.50: moderation_status = REJECTED visible_shop = false visible_catalog = false status = REJECTED → уведомление селлеру с причиной ML-модель: Спринт 0–2: Claude Haiku Vision (API call) → проверка фото (запрещённый контент) → проверка текста (spam, запрещёнка) → confidence score Спринт 3+: собственная модель + Claude fallback Защита: • Первые 3 SKU нового селлера: каталог после ручной проверки • Post-publication review: 5% случайная выборка • Жалоба покупателя → мгновенное скрытие → ручная проверка

Формула ранжирования, source_type логика, атомарный сток — всё работает одинаково и в монолите, и в отдельном сервисе.
