Информационно-логический разрыв

Архитектура ПТК описывает 11 микросервисов. Реализация (server.js) — один файл, монолит. Спецификации ПТК содержат gRPC, Kafka, Elasticsearch, ЕСИА. Реализация — Express, PostgreSQL tsvector, симуляция OTP. Это не ошибка — это стратегия.

ДВА ДОКУМЕНТА — ДВА ГОРИЗОНТА ┌───────────────────────────────────────────────────────────────┐ │ АРХИТЕКТУРА ПТК (26-nsvr_architecture_overview + 01–11) │ │ Горизонт: целевое состояние (год 2+) │ │ 11 микросервисов, gRPC, Kafka, ES, ЕСИА, КЭП │ │ «Как должно быть когда 1000+ селлеров и полный эскроу» │ └───────────────────────┬───────────────────────────────────────┘ │ │ ← РАЗРЫВ ЗДЕСЬ │ ┌───────────────────────▼───────────────────────────────────────┐ │ ПЛАН РЕАЛИЗАЦИИ (38-realization-plan + Sprint 0–2 файлы) │ │ Горизонт: сейчас → 10 недель (4 спринта) │ │ 1 файл server.js, Express, PostgreSQL, симуляции │ │ «Как работает сегодня при 5 селлерах без эскроу» │ └───────────────────────────────────────────────────────────────┘ ПОЧЕМУ РАЗРЫВ НОРМАЛЕН: 1. Стратегия монолит → извлечение. Строим монолит с правильными интерфейсами. Логика внутри — та же что в целевых сервисах. При росте → извлекаем в отдельные процессы. 2. Формулы одинаковы. calculateClearing() в server.js = calculateSplit() в Clearing Engine (09). ORDER BY ранжирования в SQL = function_score в ES. Формула та же, обёртка другая. 3. Таблицы одинаковы. 01_schema.sql содержит таблицы для Registry (10) и Marketplace (11). При извлечении — каждый сервис получает «свои» таблицы. 4. API совместимо. REST endpoints в server.js = REST в Marketplace Service (11). Тот же URL, тот же формат. Фронтенд не меняется.

Витрина — часть ПТК

Витрина — это Marketplace Service (модуль 11). Не отдельный объект. ПТК = вся система, включая витрину. Модуль 11 — самый большой по объёму и самый нагруженный, но архитектурно он стоит в ряду с остальными десятью.

ВИТРИНА ← → ПТК ПТК = 11 модулей: 01 Deal Engine FSM ← C2C (адаптирован) 02 Escrow + Contract ← C2C (адаптирован) 03 Auth Service ← C2C (адаптирован) 04 Notification + Widget ← C2C (адаптирован) 05 Widget Service ← C2C (как есть) 06 Admin Panel ← C2C (расширен) 07 Contract Builder ← C2C (расширен) 08 WebApp + Arbitrage ← C2C (адаптирован) 09 Clearing Engine ← НОВЫЙ (маркетплейс) 10 Registry Service ← НОВЫЙ (маркетплейс) 11 Marketplace Service ← НОВЫЙ (маркетплейс) = ВИТРИНА Витрина = модуль 11 = Marketplace Service Витрина ≠ отдельный от ПТК объект Витрина зависит от: Registry (10), Clearing (09), Deal (01) Витрина = самый большой модуль (~70% кода Спринтов 0–2)

Стратегия: монолит → извлечение в сервисы

СЕЙЧАС: один server.js server.js (36KB) содержит: ├── Registry endpoints ← из модуля 10 │ GET /participants, /tariffs, /bindings ├── Marketplace endpoints ← из модуля 11 │ GET /shop/{slug}, /products, /catalog/search, /cart/add │ POST /orders, /seller/{id}/products ├── Clearing logic ← из модуля 09 │ calculateClearing() внутри POST /orders ├── Bot webhook ← из модуля 11 (sub: bot) │ POST /bot/webhook/{seller_id} └── Routing middleware ← из модуля 11 (sub: routing) resolveSeller() ИЗВЛЕЧЕНИЕ (Спринт 3+): server.js → 3 отдельных процесса: marketplace-service/ ← модуль 11 ├── src/shops.js ├── src/skus.js ├── src/catalog.js ├── src/cart.js ├── src/routing.js └── src/bot.js registry-service/ ← модуль 10 (Go) ├── internal/participants/ ├── internal/tariffs/ ├── internal/bindings/ ├── internal/gate/ └── api/grpc/registry.proto clearing-engine/ ← модуль 09 (Go) ├── internal/calculator/ ├── internal/bank_adapter/ ├── internal/dispute/ └── api/grpc/clearing.proto КРИТЕРИЙ ИЗВЛЕЧЕНИЯ: Извлекаем когда: • server.js > 100KB (сложность управления) • > 50 req/sec (нагрузка на один процесс) • Нужен gRPC (Clearing ↔ Registry) • Нужна изоляция (банковский код отдельно) При 5 селлерах → монолит достаточен. При 50+ селлерах → извлечение начинается.
