Почему очередь, а не один промпт. ПТК построен наполовину и наполовину расходится сам с собой: конфигуратор каналов не влияет на выдачу, ставка канала не доходит до клиринга, режим расчёта пишется, но не читается. Агент, получивший задачу «разработай всю Систему», начнёт переписывать работающее. Пакеты идут строго по порядку, каждый опирается на закрытый предыдущий.

П5 Р3 — один источник истины видимости решение принято

Витрина фильтрует по visible_shop и visible_catalog, конфигуратор ведёт visibility_rules с приоритетом SKU > CATEGORY > SHOP, а effective_channels не вызывается в server.js ни разу. Два источника истины — тумблеры дашборда сейчас декорация. Решение от 3 сентября: источник — резолвер конфигуратора.
Витрина и каталог фильтруют товары по skus.visible_shop / visible_catalog, а конфигуратор каналов ведёт visibility_rules с приоритетом SKU > CATEGORY > SHOP, и функция effective_channels не вызывается в server.js ни разу. Два источника истины. Решение принято: источник истины — резолвер конфигуратора. Маршруты витрины и каталога спрашивают effective_channels. Поля visible_shop и visible_catalog становятся производной и пересчитываются синхронно при изменении любого правила. Записывает их только резолвер: ручное редактирование видимости в форме SKU закрывается, поле становится read-only с отсылкой к конфигуратору. Не ломай существующие ответы API — контракт для фронта остаётся прежним. Не делай флаг режима и две реализации: резолвер вызывается всегда, ветвления в коде быть не должно.
Приёмка
Тумблер в дашборде каналов меняет реальную выдачу витрины. Тест-кейс Масса Мадре — три схемы на трёх категориях — отрабатывает. Храповик по-прежнему запрещает понижение. Поля visible_shop и visible_catalog поддерживаются в актуальном состоянии; таблицы правил не удаляются.
В пул
Видимость SKU глазами селлера, дашборд каналов, составные витрины — снять пометки «читает, не пишет».

П6 Р4 — take_rate доходит до клиринга после П5

Сплит берёт единый ORGANIZER_FEE, ставка канала из конфигуратора до клиринга не доходит.
Сплит в POST /orders берёт единый ORGANIZER_FEE, а take_rate канала из конфигуратора до клиринга не доходит. Проведи ставку канала в расчёт сплита. Сохрани инварианты: ставка берётся строкой из participant_tariffs с проверкой срока, а не константой в коде; сумма сплитов равна total_amount; структура формулы FULFILLMENT / LOGISTICS / ORGANIZER / SELLER не меняется. Прогони эталон ORD-00001: SELLER 817.16, FULFILLMENT 600, LOGISTICS 350, ORGANIZER 2.84.
Приёмка
Эталон сходится. Заказ через канал с иной ставкой даёт иной сплит, сумма по-прежнему равна total_amount. Смена ставки — вставка строки, кода не касается.

П7 Р5 — режим расчёта в заказе решение принято

settlement mode пишется в settlement_rules, но POST /orders его не читает. Решение от 6 сентября: режим задаётся правилом, покупатель его не выбирает. Стартовая конфигурация Масса Мадре — SYSTEM на весь ассортимент.
settlement mode (OWN / SYSTEM / PER_ORDER) пишется в settlement_rules, но POST /orders его не читает. Решение принято: режим расчёта определяется правилом, покупатель его не выбирает. Заказ при создании спрашивает резолвер settlement_rules и записывает полученный режим в orders. Стартовая конфигурация Масса Мадре — SYSTEM на весь ассортимент. Эскроу обязателен для режима SYSTEM. Цифровая валюта не поддерживается ни в каком режиме (ст. 20). Выбор способа расчёта на чекауте не делай — контракт API для фронта не меняется, дополнительных полей в теле запроса не появляется. Флага режима и двух реализаций быть не должно: резолвер вызывается всегда. Ставку удержания в код не зашивай — она берётся строкой из participant_tariffs с проверкой срока.
Приёмка
Заказ несёт режим расчёта. SYSTEM идёт в эскроу-контур, OWN не попадает в клиринг Системы. Переключение не ломает существующие заказы.
В пул
Механизмы расчёта Масса Мадре — выбранный помечается принятым, два других остаются рассмотренными.

П9 Тесты L2/L4 и процедура развёртывания ждёт площадки

Уровни L1 закрыты, L2 браузерный и L4 сквозной — нет. Процедура развёртывания пишется под конкретную площадку, а она не зафиксирована.
Собери браузерный чек-лист L2 и сквозной сценарий L4 по плану тестирования пути селлера: вход селлера, магазин, товар, витрина, корзина, заказ, клиринг — со ссылками на ID кейсов плана. Отдельно напиши процедуру развёртывания на ПЛОЩАДКА: миграции по порядку, переменные окружения с обязательными проверками, порядок первого запуска, smoke-test как приёмочный шаг, откат.
Приёмка
Сценарий проходится на живом стенде целиком. Процедура воспроизводится с нуля на чистой базе.
В пул
План тестирования — отметка по L2 и L4. Гайд развёртывания — новая площадка.
