Кто есть кто: ЛК, API, база, витрина

Концептуальная схема ролей — чтобы не путать инструмент с данными. Личный кабинет, Marketplace API, база и витрина делают разное: один вводит, другой переносит, третий хранит, четвёртый показывает. Метафора — ресторан: пульт, официант, кухня, зал.

Дополняет: техническую схему составных частей (те же элементы, но с реальными маршрутами и полями). Здесь — про роли и смысл, там — про механику.

Развеиваем путаницу

✗ как часто думают

«ЛК = магазин селлера» — будто кабинет и есть магазин.

«Marketplace API = каталог» — будто API и есть каталог товаров.

✓ как на самом деле

ЛК — инструмент управления магазином. Магазин — запись shops + витрина. Кабинет ими управляет, но сам магазином не является.

API — посредник (код server.js). Каталог — срез данных skus с visible_catalog=TRUE, который API отдаёт агенту.

Место витрины — и чем она отличается от агента. Витрина и агент оба читают из базы, но это разные окна. Витрина — окно к данным одного магазина: показывает его бренд и его товары (visible_shop=TRUE), это лицо конкретного магазина, его «зал». Агент — окно к каталогу многих магазинов сразу: срез skus с visible_catalog=TRUE со всей Системы, это «официант, обходящий все залы». Один товар может быть виден и там, и там, но витрина всегда про один магазин, а агент — про весь каталог.
Где живут «магазин» и «каталог». Оба — не интерфейсы, а данные в базе. Магазин — запись в shops (плюс витрина, которая её показывает). Каталог Системы — срез skus с visible_catalog=TRUE. Кабинет и витрина — лишь окна к этим данным: одно чтобы вводить, другое чтобы показывать.
Почему это важно не путать. Если считать «ЛК = магазин», кажется, что у каждого селлера свой отдельный сервер-магазин. На деле магазин — строка в общей базе, а кабинет и витрина — общие интерфейсы, отличающиеся только тем, какие данные показывают. Это и есть инвариант Системы: один API, одна база, много окон — что делает возможным и единый каталог для агента, и честные общие правила расчёта.
