Проблема: почему нельзя «каждый с каждым»

В многосторонней сделке участвуют 4–6 сторон. Если каждый заключает договор с каждым — это N×N связей, и система становится неуправляемой.

N×N МОДЕЛЬ (так НЕ делаем) 5 участников заказа: Покупатель, Селлер, Фулфилмент, Логистика, Организатор Договоры: Покупатель ↔ Селлер (купля-продажа) Покупатель ↔ Логистика (доставка) Селлер ↔ Фулфилмент (сборка) Селлер ↔ Логистика (транспорт) Селлер ↔ Организатор (комиссия) Фулфилмент ↔ Логистика (передача) Фулфилмент ↔ Организатор (условия) Логистика ↔ Организатор (условия) Покупатель ↔ Организатор (оферта) ... и на каждый заказ — акты, счета, сверки между КАЖДОЙ парой = 10+ договоров, 10+ денежных потоков, 10+ точек спора Проблемы N×N: · Селлер должен заключить договор с КАЖДЫМ фулфилментом и логистикой · При смене фулфилмента → новый договор, новые реквизиты, новый акт · При споре — неясно кто кому что должен · Покупатель заключает договор с логистикой, которую не выбирал · Масштаб: 10 селлеров × 3 фулфилмента × 2 логистики = 60 договоров

Решение: звезда (ст. 2 Правил)

Все участники заключают договор только с Организатором. Не друг с другом. N участников = N договоров, а не N×N. Организатор — центр расчётов и арбитр.

ЗВЁЗДНАЯ МОДЕЛЬ (так делаем, ст. 2.1) ┌───────────────┐ │ ОРГАНИЗАТОР │ │ центр звезды │ │ арбитр │ │ клиринг │ └───────┬───────┘ │ ┌───────────────┼───────────────┐ │ │ │ ┌──────▼──────┐ ┌──────▼──────┐ ┌──────▼──────┐ │ СЕЛЛЕР │ │ФУЛФИЛМЕНТ │ │ ЛОГИСТИКА │ │ Договор │ │ Договор │ │ Договор │ │ присоедин. │ │ присоедин. │ │ присоедин. │ │ + тарифы │ │ + тарифы │ │ + тарифы │ └─────────────┘ └─────────────┘ └─────────────┘ Между селлером и фулфилментом: нет договора Между селлером и логистикой: нет договора Между фулфилментом и логистикой: нет договора Каждый подписал одно соглашение — с Организатором. Организатор клирингует расчёты (ст. 6). Услуга оказывается напрямую, деньги идут через центр. 10 селлеров × 3 фулфилмента × 2 логистики = 15 договоров (а не 60 при N×N)
Аналогия: платёжная система (ст. 2.2). Visa не заключает договор магазина с банком покупателя. Visa — центр, через который идут расчёты. Магазин подключён к Visa, банк подключён к Visa. Между ними — процессинг. Наша модель — то же самое для логистики и фулфилмента.

Три слоя отношений

Отношения участников устроены на трёх слоях: юридический (договоры), операционный (кто что делает) и финансовый (кто кому платит). Слои не совпадают — и в этом сила модели.

СЛОЙ 1: ЮРИДИЧЕСКИЙ (договоры) Каждый участник ←→ Организатор Документ: Договор присоединения к Правилам (ст. 7) Содержание: права, обязанности, SLA, тарифы, порядок выхода Подпись: click-wrap (ФЛ/ИП) или КЭП (ООО) Связей: N (по числу участников) Селлер НЕ заключает договор с фулфилментом. Фулфилмент НЕ заключает договор с логистикой. Покупатель акцептует публичную оферту Системы. СЛОЙ 2: ОПЕРАЦИОННЫЙ (кто что делает) Услуга оказывается НАПРЯМУЮ: ┌──────────┐ ┌──────────────┐ ┌──────────┐ │ Селлер │────→│ Фулфилмент │────→│Логистика │ │ производит │ собирает │ │доставляет│ │ товар │ │ упаковывает │ │ │ └──────────┘ └──────────────┘ └──────────┘ │ ▼ ┌──────────────┐ │ Покупатель │ │ получает │ └──────────────┘ Операционная связь: селлер → фулфилмент → логистика → покупатель. Но денежная связь — через Организатора (слой 3). СЛОЙ 3: ФИНАНСОВЫЙ (кто кому платит) Покупатель ──→ ЭСКРОУ (банк) ──→ КЛИРИНГ ──→ N получателей │ │ │ Организатор │ │ считает доли │ │ по тарифам │ │ из реестра │ │ │ ▼ ▼ ┌─────────────────────────────┐ │ Селлеру: остаток │ │ Фулфилменту: по тарифу │ │ Логистике: по тарифу │ │ Организатору: 0,2% │ └─────────────────────────────┘ Селлер НЕ платит фулфилменту. Покупатель НЕ платит логистике. Все получают из одного эскроу через клиринг.
Почему слои разделены (ст. 3). Если бы Организатор определял стоимость услуги — он бы её перепродавал (посредник). Но он только клирингует: тариф назначает сам участник (оферта в реестре, ст. 3.2), состав выбирает селлер (ст. 3.3), объём определяется заказом (ст. 3.4). Организатор вычисляет сумму = объём × тариф и расщепляет эскроу.

Реестр: тарифы как оферта (ст. 3.2)

Каждый участник при вступлении публикует тарифы в реестре. Тарифы — это оферта внутри Системы: «готов оказать услугу за такую-то цену». Селлер видит тарифы и выбирает.

Привязка: селлер выбирает операторов (ст. 3.3)

При настройке магазина селлер выбирает, какие операторы обслуживают его заказы. Это не договор — это привязка (binding) внутри Системы. Можно поменять без нового договора.

ПРИВЯЗКА «СЕЛЛЕР ↔ НАБОР ОПЕРАТОРОВ» Селлер: Масса Матере (PTR-12345) ├── Фулфилмент: 3PL-Сервис (PTR-67891) ← выбран из 2+ в реестре ├── Последняя миля:Курьер-Экспресс (PTR-88901) ├── Магистраль: — (пока не нужна, МСК) └── Склад: СкладСервис (PTR-55501) Как фиксируется: Registry Service → infra_bindings table { seller_id: "PTR-12345", fulfillment_id: "PTR-67891", logistics_id: "PTR-88901", warehouse_id: "PTR-55501", trunk_id: null, bound_at: "2027-07-01", active: true } Что видит селлер в ЛК: ┌──────────────────────────────────────────┐ │ Мои операторы │ │ │ │ 📦 Фулфилмент: 3PL-Сервис │ │ Сборка: 200₽/ед │ SLA: 24ч │ │ [Сменить ▾] │ │ │ │ 🚚 Доставка: Курьер-Экспресс │ │ Зона 1: 350₽ │ SLA: 24ч │ │ [Сменить ▾] │ │ │ │ 🏭 Склад: СкладСервис │ │ 40₽/палл/день │ │ [Сменить ▾] │ └──────────────────────────────────────────┘ Смена оператора: · Селлер нажимает «Сменить» → видит список из реестра с тарифами · Выбирает нового → привязка обновляется · Текущие заказы доводятся по старому оператору · Новые заказы → по новому · Нового договора НЕ нужно — оба оператора уже в Системе
Свобода выбора (ст. 13.3). Когда в роли ≥2 участника, селлер реально выбирает. До этого (Волна 0–1) — «рекомендованный партнёр», фактически единственный. Привязка автоматическая из гейта.

Анатомия заказа: что происходит при покупке

Заказ — это момент, когда все три слоя (юридический, операционный, финансовый) соединяются в одну сделку. Ни один участник не подписывает ничего нового — всё уже зафиксировано в Правилах, реестре и привязках.

Почему это работает. Формула расщепления = объём × тариф (ст. 3.5). Все три входа заранее известны: тариф из реестра, состав из привязки, объём из заказа. Организатор не принимает решений — вычисляет. Это убирает конфликт интересов и юридический риск «перепродажи».

Без эскроу (Трек A, Волна 0–1)

Пока банк API не подключён — оплата напрямую. Клиринг ручной.

На каждый заказ НЕ подписывается новый договор. Договор присоединения подписан один раз при вступлении. Это как с Visa: на каждую покупку не подписывают договор — просто проходит транзакция по правилам системы.

Ценообразование: кто что назначает

В Системе нет единого «прайс-листа». Каждый участник назначает свои тарифы самостоятельно. Организатор не определяет цены — он только клирингует. Это принципиальное отличие от маркетплейса, где платформа диктует комиссии.
